# Правила разработки и рефакторинга UI-компонентов

## 1. Strictly UI-Kit Only (Никаких кастомных стилей)
- Все компоненты и секции строятся исключительно из примитивов `@blueprint/ui-kit`:
  - `Modal`, `Modal.Body`, `Modal.Footer`
  - `Section`, `Section.Header`, `Section.Body`
  - `Text`, `Badge`, `Button`, `Icon`, `Input`, `Textarea`, `Select`, `Tabs` и др.
- **Запрещено** создавать кастомные `.module.css` или inline-стили для оберток, если задачу можно решить композицией компонентов дизайн-системы.

## 2. Атомарность и максимальная переиспользуемость (Паттерн *Badge)
- Выделять маленькие, самодостаточные атомарные компоненты для метаданных (`SalaryBadge`, `LocationBadge`, `WorkplaceBadge`).
- Один и тот же бейдж должен переиспользоваться без изменений:
  - в карточке канбан-доски (`KanbanCardMetaRow`);
  - в шапке модального окна (`VacancyModalHeader`);
  - в любых других сводных представлениях.

## 3. Прямой поток данных (Никаких Props-билдеров)
- **Исключить** промежуточные мега-функции вроде `buildHeaderAndSalaryProps`, `buildContentSectionProps`, `buildCompatibilityProps`.
- Данные и колбэки передаются напрямую из моделей (`vacancy`) или контроллеров (`ctrl`) в пропсы дочерних компонентов.
- Избегать проброса избыточных объектов или массивов целиком туда, где нужны конкретные примитивы.

## 4. Локализация по месту (i18n inside)
- Не передавать переведенные строки, лейблы кнопок и плейсхолдеры через пропсы снаружи.
- Каждый компонент сам вызывает `useTranslation()` и использует `t('...')` непосредственно в месте рендера.

## 5. Порядок реализации и декомпозиция модалки
- Двигаться строго **по одному компоненту сверху вниз**.
- Временные исключения (оставлять комментарии-заглушки):
  - `VacancySalarySection` (пока не делаем)
  - `VacancyDescriptionSection` (пока не делаем)
- Разделение блока AI:
  - `VacancyAiSummarySection` (AI саммари + кнопка перегенерации через `Section`)
  - `VacancyCompanySection` (Информация о компании через `Section`)
- Никаких авто-коммитов в git без явной команды пользователя.
