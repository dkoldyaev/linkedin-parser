### Оценка сложности SQL — без метрик времени

На синтетических 80 пользователях, 32 000 карточек и 32 000 событиях истории выполнен PostgreSQL `EXPLAIN` без `ANALYZE`.

* Страница карточек: index-only scan по `(user_id, updated_at, id)`; сложность выбора страницы `O(log N + L)`.
* URL-дедупликация: индекс `(user_id, url)`; `O(log N)`.
* Новые карточки пользователя: `(user_id, created_at)`; `O(log N + R)`.
* История карточки: `(vacancy_id, created_at)`; `O(log H + R)`.
* Единственный осознанно оставшийся линейный путь — substring-поиск `ILIKE '%term%'`, который читает только карточки текущего пользователя. Для него следующий этап — trigram index и cursor pagination/summary endpoint, если продукт подтвердит необходимость поиска по большим доскам.

При 120 запросах с параллелизмом 4 ошибок не было; каждый маршрут сохранял постоянное число SQL round trips: карточки — 5, tags — 3, stats — 5, настройки — 7, очередь — 2. Результаты: `docs/audit-query-plans.json` и `docs/audit-read-load-results.json`.
